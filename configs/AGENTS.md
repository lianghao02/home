## 1. 核心開發原則與停止條件

1. **先讀後改**：先讀取理解既有專案架構、檔案內容與前次交接狀態，再進行修改。不得僅依記憶推測現況。
2. **最小修改**：優先以最小異動達成需求，不因單一功能隨意重構無關模組。
3. **功能相容**：維護既有功能完整性，確保修改不破壞原本可運作的功能。
4. **真實驗證**：完成修改前必須透過工具或指令進行實際驗證，不虛構測試結果。能透過測試驗證的規則，優先透過測試或實測驗證，不單純依賴提示詞約束。
5. **完成判定與 Agent 停止條件（嚴禁無限發散修改）**：
   - **問題分類原則**：
     - **阻斷性問題（必須處理）**：程式無法執行、核心功能失效、資料毀損遺失、明確安全隱患、明確違反業務需求。
     - **重要問題（當次修正）**：高機率誘發異常、重度效能瓶頸、高風險維護盲點、已能實際重現之 Bug。
     - **改善建議（不得阻礙交付）**：架構再抽象化、套用最新語法/框架、理論極限效能、UI 主觀微調、假設性邊界問題、低風險 Lint 警告。
   - **停止條件**：當使用者需求已達成、主要功能正常、必要測試與實測通過、無阻斷性問題與重大風險時，**即判定「目前版本可交付」，立即停止擴大修改**。嚴禁以追求「零警告、零 TODO、完美架構、最新框架、理論最佳效能」為由持續修改正常運作的程式碼。

## 2. 安全、防禦與環境規範

- **高風險操作防禦**：涉及批次刪除、覆寫、搬移或不可逆操作時，優先提供預覽/模擬模式或確認機制，再進行實際執行。UI 與記錄應明確提示原始檔案變更狀態。
- **Git 操作安全與工作目錄防護**：
  - 開始任務與結束交付前，必須以 `git status` 確認分支與工作目錄狀態。
  - 未知之未提交修改絕對不得覆寫、stash 丟棄或抹除；遇到非 Clean 狀態應優先釐清或停止回報。
  - 嚴禁無授權的 `git reset --hard`、`git clean -fdx`、force push 或破壞性遠端對齊操作。
  - 提交與推播前確認分支與 remote 正確，禁止把其他工作階段之修改混入本輪 Commit。
- **敏感資訊隔離**：API Key、密碼、Token 嚴禁硬編碼在程式碼或版本庫中。
- **路徑與環境強健性**：
  - 避免硬編碼本機絕對路徑，統一使用相對路徑或動態路徑取得機制。
  - Windows 環境相容：文字檔案讀寫應明確指定編碼（預設優先使用無 BOM 的 UTF-8；特定 CSV 或公務系統資料依來源編碼處理）。二進位檔案（圖片、Excel、PDF 等）嚴禁套用文字編碼參數。
- **BAT 與 PowerShell 腳本原則**：
  - **BAT 僅作薄啟動器（Thin Launcher）**：BAT 僅負責固定工作目錄、尋找合適之 PowerShell 執行檔、以無干擾參數啟動對應 `.ps1`、必要時暫停 (`pause`)；所有邏輯運算、外部命令呼叫與錯誤捕捉均置於 PowerShell。
  - **編碼防禦**：涉及中文路徑、Console、文字檔案、外部程式（Git、Python、dotnet）輸入輸出時，嚴禁單純依賴系統預設 Code Page，腳本開頭應統一設定 UTF-8 編碼環境。
  - **路徑規範**：PowerShell 內部路徑計算一律優先使用 `$PSScriptRoot` 與 `Join-Path`，嚴禁寫死使用者個人路徑。
- **Repository 潔淨防線**：
  - **版本庫保存邊界**：Git 僅保存正式原始碼、必要測試、設定範例與核心文件。依語言嚴格設定 `.gitignore`，禁止長期提交依賴包（`.venv`, `node_modules`）、編譯輸出（`bin`, `obj`, `dist`, `build`）、快取與日誌（`cache`, `log`, `temp`）、本機設定檔與非必要大型測試資產。
  - **拒絕備份污染**：Git 本身即為版本歷史庫，禁止在儲存庫中長期保留 `old/`, `backup/`, `final/`, `dist-old/`, `legacy-v1/` 等冗餘備份目錄，僅在有回歸對比或相容必要時保留明確標註之過渡檔案。

## 3. 工程交付與架構標準

### 3.1 交付標準
依任務範圍提供足以直接套用的完整內容；局部修改可只交付明確可替換區段，較大修改則提供完整檔案，避免給予無法判斷插入位置的碎片。

### 3.2 參數集中管理 (Config-First)
程式中的可調整參數（閾值、路徑、模型名稱等）應集中置頂管理，避免魔術數字。僅在確實需要環境變數切換時引入 `.env`，不強制增加不必要的套件依賴。

### 3.3 簡潔、架構適當性與 UI/UX 共通語意
- **Web 與架構簡潔性**：優先採用最簡單且足以維護的架構。若單檔 HTML 結構清晰，不因功能數量單獨決定重構；僅在複雜度、可測試性或維護成本確實需要時升級模組化或框架。不要為了專案成長而盲目引入大型前端框架。
- **字型與樣式**：介面優先採用適合臺灣 Windows 環境的系統字型堆疊（如 `Microsoft JhengHei`、`Segoe UI`、系統預設無襯線字型）；僅在明確要求特定品牌視覺且允許網路依賴時才引入外部 Web Fonts。
- **UI/UX 核心語意（統一設計語言，不統一版型）**：
  - 各工具依業務型態維持最適版型（如監控中心、影音工作站、批次轉檔佇列、地圖核心、精簡卡片），不強求版型齊一。
  - 全域統一**視覺語意基底**：色彩層次（如莫蘭迪色系調性）、控制項高度與圓角、狀態顏色（成功、進行中、警告、錯誤）、危險操作防護視覺、長時間耗時任務之進度與取消回饋。
  - **狀態透明優先於美觀**：使用者介面首要任務是讓使用者第一眼清晰辨識：
    1. 目前處於什麼狀態。
    2. 程式正在執行什麼操作。
    3. 下一步是什麼。
    4. 任務是否已完成。
    5. 若失敗，明確原因與阻斷點為何。
    6. 使用者現在可以採取什麼補救或後續動作。

### 3.4 任務領域與語言選型矩陣 (Technology Selection by Domain)
新專案建立或既有架構評估時，應依任務領域與效能邊界選擇最適語言，避免盲目使用單一語言：

| 任務領域／業務情境 | 首選語言與技術棧 | 選型理由與核心邊界 |
|:---|:---|:---|
| **AI 深度學習／視訊鑑識／快速 MVP 探索** | **Python (3.13+)** | 生態系最完整（PyTorch、YOLO、OpenCV、PyAV），原型驗證與算法調校速度最快。主程式漸大時應以模組化、狀態模型與測試深化，而非隨意更換語言。 |
| **Windows 系統工具／底層 Win32／Office COM** | **C# (.NET 8/9 / Native AOT / WPF)** | Windows 第一公民；原生 Win32、登錄檔與 COM 物件生命週期管理；可編譯為 10MB 單檔免安裝 Exe。維護穩定，不隨意遷往 Electron 或未成熟框架。 |
| **CPU 密集運算／海量檔案去重／高效能桌面 App** | **Rust (Tauri / Rayon)** | 零 GC 負擔、多核心極限並行（如 dHash、ZIP 串流）、極致記憶體安全與原子檔案交易。 |
| **輕量資料解析／地圖軌跡／免安裝純前端工具** | **純 Web (HTML5 / Vanilla JS / Canvas)** | 零環境依賴、瀏覽器即開即用、搭配設計系統提供輕盈視覺。不隨意引入重量級 SPA 框架。 |
| **公務網頁爬蟲／行政自動化** | **Python (Playwright / Selenium / PySide6)** | 具備動態 DOM 解析與題庫對齊之高度彈性，因應外部網站改版之維護成本最低。穩定運作之流程不因追求新穎技術隨意替換底層引擎。 |

- **演進原則（Prototype in Python, Scale in C#/Rust）**：複雜工具允許在初期以 Python 快速驗證核心邏輯；當業務規則與測試穩定後，若追求秒開與極致分發，應主動評估遷移至 C# 或 Rust。

### 3.5 純前端專案之桌面化封裝標準 (Desktop Packaging Standards)
針對純 HTML5 / JavaScript 開發之工具（如基地台定位、影像處理、金融解析、行事曆等），若需封裝為獨立離線桌面應用程式：
- **首選封裝框架**：**Tauri (Rust + Windows Edge WebView2)**。
  - **極致輕量**：打包後體積僅 **3MB ~ 5MB**（直接複用 Windows 內建 WebView2，零自帶瀏覽器內核負擔）。
  - **零 UI 重寫成本**：100% 複用既有 HTML/CSS/JS 業務代碼。
  - **原生能力擴展**：透過 Tauri Rust 核心安全存取本機檔案系統、大容量快取與原生檔案對話框。
- **避免使用**：除非有無法取代的 Node 原生模組依賴，**嚴禁無特殊理由引入 Electron**（避免產生 150MB+ 臃腫體積與記憶體浪費）。

## 4. 專案文件原則與多 Agent 協作連續性機制

依專案實際複雜度建立必要文件，不為湊齊架構而新增空白或低價值文件。

### 4.1 核心文件職責劃分與 Source of Truth
專案治理文件權限與真理來源（Source of Truth）明確劃分如下，彼此不重複保存相同資訊：
- `00_Dev-Control-Center/configs/AGENTS.md`：**全域工作規則**與開發憲法最高指導。
- 各 Repository `AGENTS.md`：**專案長期邊界**與不可違反的規則例外（不複製全域憲法）。
- 各 Repository `HANDOFF.md`：**當前工作交接斷點**（回答上一個 Agent 做到哪裡、Git 狀態與下一步）。
- `00_Dev-Control-Center/IMPROVEMENTS.md`：**跨專案已確認改善總表**（全域唯一彙整表，各 Repository 不自建）。
- Git Commit / Diff：**實際修改歷史與驗證證據**（README、ARCHITECTURE、DESIGN、MEMORY 不重複保存歷史流水帳）。
- `README.md`：專案定位、下載、安裝與使用說明。
- `ARCHITECTURE.md`：系統架構、模組切分與資料流。
- `DESIGN.md`：UI/UX 規格、資訊架構與操作流程（僅在複雜介面專案需要時建立）。
- `spec.md` / `plan.md` / `tasks.md`：中大型工作階段之需求規格、實作路徑與原子任務。
- `MEMORY.md`：具長期價值的重大架構決策與踩坑歷史（不記流水帳）。
- `CHANGELOG.md`：版本變更歷程（有正式發布需求時維護）。

**治理文件衝突判斷優先順序**：
若治理文件內容互相衝突，依下列原則判斷：
1. 使用者當次明確要求
2. 專案 `AGENTS.md` 的專案長期邊界
3. 最新有效 `HANDOFF.md` 的當前工作狀態
4. `IMPROVEMENTS.md` 的待辦與暫緩狀態
5. Git Commit / Diff 與 Working Tree 的實際證據

其中 Git 實際狀態用於驗證「實際做了什麼」，不得因文件宣稱完成而忽略實際 Git 狀態。

### 4.2 雙 Agent 協作與輪替交接規範
- **共用單一交接檔**：Codex 與 Antigravity 共用單一 `HANDOFF.md`，嚴禁建立 `CODEX_HANDOFF.md`、`ANTIGRAVITY_HANDOFF.md` 或個人專屬備忘錄。
- **單一主責原則**：同一輪只指定一個主責實作 Agent；Agent 角色可互換，不固定誰實作、誰 Review。
- **更新責任歸屬**：完成、中斷或移交任務時，由**當前主責 Agent** 負責更新 `HANDOFF.md`；下一個 Agent 不應重新代為整理前一輪工作。
- **成果繼承**：已完成、已驗證的工作不因換 Agent 而重新開始或全盤推翻。
- **HANDOFF 標準欄位結構**：
  ```markdown
  # HANDOFF

  ## 目前狀態
  可交付 / 進行中 / 待驗證 / 阻塞

  ## 本輪目標

  ## 已完成

  ## 刻意未修改

  ## 尚未完成

  ## 驗證結果
  ### 已執行
  ### 尚未驗證
  ### 已知風險

  ## Git 狀態
  - Commit：<SHA 或「未提交」>
  - Push：是 / 否
  - Working Tree：Clean / Modified
  - Branch：<分支名稱>

  ## 下一步
  ```

### 4.3 Agent 中斷與額度不足處理程序
當 Agent 因額度不足、工作階段中斷、工具限制或環境限制無法繼續時：
1. **立即停止開新工作**：不強行啟動下一階段修改。
2. **整理至安全中斷點**：確保代碼處於語法完整、可編譯或可安全還原之狀態。
3. **部分交付 Commit**：可獨立成立且完成必要驗證之部分，先行 Commit 保存進度。
4. **誠實記錄 HANDOFF**：尚未完成與尚未驗證之項目誠實寫入 `HANDOFF.md`，嚴禁假裝完成或未測標已測。
5. **平順接手**：下一 Agent 從中斷點平順接手，Push 依當前安全狀態決定，不設為無條件強制推播。

### 4.4 最小必要驗證原則
- **修改範圍對齊**：依本輪實際修改範圍進行針對性驗證，不要求因局部微調而重跑所有無關的重量級測試。
- **核心驗證不可省**：受影響之核心功能、進入點與語法檢驗不得省略。
- **HANDOFF 驗證載明**：交接檔必須明確列出「已執行測試與結果」、「尚未驗證項目」與「已知潛在風險」。
- **交付標記底線**：關鍵核心驗證未完成前，絕對不得標註為「可交付」。

### 4.5 Agent 接手之最小讀取範圍
為避免 Token 浪費與上下文混亂，Agent 接手專案時預設依序讀取：
1. 全域 `configs/AGENTS.md`
2. 專案 `AGENTS.md`
3. 專案 `HANDOFF.md`
4. `00_Dev-Control-Center/IMPROVEMENTS.md` 中該專案段落
5. 最新相關 Commit / Diff
6. 本輪任務必要程式碼

只有在既有資訊不足時才逐步擴大讀取 Repository。**嚴禁無理由每次重新全面掃描專案檔案**。

### 4.6 Reviewer 範圍與停止循環機制
副 Agent 或 Review 角色介入時：
- **審查範圍限制**：預設僅 Review 本輪 Diff、受影響的核心邊界與必要測試結果，不借題發揮審查無關模組。
- **三級分類**：
  - **阻斷**：造成系統崩潰、資料遺失、核心功能失效（必須修正）。
  - **需修**：具體重現之 Bug、高風險邊界漏洞（當輪修正）。
  - **建議**：主觀風格、理論極限、語法優雅度（**不得阻止交付**）。
- **停止審查循環**：無阻斷性與重要問題後立即停止，嚴禁陷入無限 Review 循環。

## 5. Git Commit 語法

遵循 Conventional Commits 小寫格式 `type: 台灣繁體中文簡述`：

| Type | 適用情境 |
|------|---------|
| `feat` | 新增功能 |
| `fix` | 修復 Bug |
| `refactor` | 重構（不影響行為） |
| `docs` | 文件更新 |
| `sync` | 同步上游或外部依賴 |
| `chore` | 雜項維護（CI、設定調整） |
| `perf` | 效能優化 |
| `design` | 視覺/UI 重構 |

## 6. Skill 載入與路由規則

> **AGENTS.md 負責「核心行為準則」；Skills 負責「專屬領域工法」。**

僅在滿足特定情境時，主動載入並參考對應 Skill：

| 觸發情境 | 載入 Skill |
|---------|------------|
| GitHub 搜尋、upstream 同步、PR、Release CI/CD、外部 Repo 引用 | `github-workflow` |
| 撰寫版本發布說明 (Release Note)、更新 `CHANGELOG.md` | `release-notes` |
| Web 前端 Core Web Vitals 效能量測與針對性優化 | `addyosmani-perf` |
| 公務/對外系統之 WCAG 無障礙合規需求或明確要求無障礙掃描 | `accesslint` |
| 大型新專案、跨模組功能、架構重構或需要跨工作階段保存進度 | `project-planning` |
| 準備交付、提交、推送、建立 PR 前之 Git、測試、Web 實測與敏感資料檢核 | `project-readiness-check` |
| Playwright 瀏覽器自動化測試、UI 視覺驗證 | `webapp-testing` |
| PDF、Word、Excel、PowerPoint 等本機文件轉為分析用 Markdown | `document-to-markdown` |
| 建立、重構或驗證新的 Skill 本身 | `skill-creator` |
| **使用者明確指定** `caveman` / 極簡 / 省 Token 模式時 | `caveman` |
